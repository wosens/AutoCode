- 调研日期：2026-10-29（GitHub 数据当日经 API 逐一核实）
- 需求来源：开发一个「方便查看源码」的模块，形态为动态库、纯 C 导出接口
- 说明：本报告为选型调研，未写任何代码；所有星数/许可证/活跃度数据均以 GitHub API 或官方页面当日返回为准

## 1. 需求拆解

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 代码块高亮 | 关键字、常量（数字/字符串）、变量、函数名、注释等分类着色 |
| F2 | 光标名称高亮 | 光标处所在名称高亮，且全文其他位置的相同名称一并高亮（即 Notepad++ 的 Smart Highlighting / IDE 的 Identify-in-file） |
| F3 | 括号配对高亮 | 按当前光标位置自动高亮前后配对的 `()` / `{}` / `[]`（不配对时警示色） |
| 形态 | 动态库 + 纯 C 接口 | 宿主语言无关，导出 `extern "C"` 函数集 |

一个必须提前指出的口径问题（影响选型）：

- F1 中「变量、函数名分别不同颜色」是**语义级**需求。传统轻量 lexer（Scintilla/Lexilla、Kate XML 规则、QCodeEditor 的 QRegExp 规则）只能做到**词法级**：关键字/字符串/数字/注释可精确分类，「标识符」只能统一给一色或粗分（如 C++ lexer 不区分函数调用名与变量名）。要做到真正的函数名/变量名/类型名分层着色，需要**语法/语义层**：
  - tree-sitter：语法树可区分 `function`、`variable.parameter`、`type` 等 capture（标准 capture 名见 tree-sitter-highlight 文档）；
  - 或者调用方自带符号表/LSP（超出本模块范围）。
- F2 的「相同名称高亮」同样有两档：词法档（全文本字符串匹配，Notepad++ 式）与语义档（只高亮同一符号的引用，tree-sitter/LSP 才能做）。词法档实现简单、效果通常够用。

## 3. 逐项详评

### 3.1 Scintilla + Lexilla（官方编辑控件 + 官方 lexer 库）★ 推荐主案

- 组成：Scintilla 5.x 负责**控件**（Windows 下就是 HWND 子窗口，API 全部是 `SendMessage(msg, wParam, lParam)`，天然就是纯 C 调用形态）；Lexilla 负责**lexer**（共享库 lexilla.dll，2024 起从 Scintilla 拆出独立演进）。
- 许可：Scintilla/Lexilla 历史许可（License.txt）允许「any free project or commercial product」使用，闭源商用无障碍（比 GPL 家族友好得多）。
- 与三项需求的对应（消息均已在 ScintillaDoc.html 逐条核实存在）：
  - F1：`CreateLexer("cpp")`（Lexilla C 导出）+ `SCI_SETILEXER` + `SCI_STYLESETFORE` 设色 + `SCI_SETKEYWORDS` 供关键字表；词法级分类齐全（SCE_C_WORD/SCE_C_STRING/SCE_C_NUMBER/SCE_C_COMMENT/SCE_C_IDENTIFIER…）。
  - F3：`SCI_BRACEMATCH`（求配对位置）+ `SCI_BRACEHIGHLIGHT` / `SCI_BRACEBADLIGHT`（配对/失配高亮），控件原生支持，一行消息即可。
  - F2：指示器体系 `SCI_INDICATORFILLRANGE`（Notepad++ 的 Smart Highlighting 同机制），光标取词后全文扫描填充指示器即可。
- C 接口适配成本：几乎为零。Lexilla 协议文档明确写了 C 用法（「For C, ILexer.h should not be included... from C, void* is used instead of ILexer5*」），其 DLL 导出 `CreateLexer` 等即 C 可加载的函数。
- 动态库形态：自己的 CodeView.dll 内部创建 Scintilla 控件（`::CreateWindow("Scintilla",...)`），对外导出纯 C 函数集；Scintilla 提供静态链接或 scintilla.dll 两种用法。
- 现状与风险：
  - 极活跃：v5.6.7 于 2026-09 发布（「decreases memory used for layout」），Lexilla 仓库 2026-10-27 仍有推送。
  - 注意大版本迁移成本：5.0 曾把 lexer 拆到 Lexilla 并升级 ILexer5 接口；建议 vendored 固定版本，不盲追主线。
  - 局限：词法级高亮——函数名 vs 变量名不区分（见 §1 口径说明）；若接受「标识符统一色」即可满足，这是集成成本最低、功能最全的方案。

### 3.2 tree-sitter（纯 C 增量解析器）★ 语义层推荐 / 组合件

- GitHub 27320★ MIT，GitHub.com 自家的代码高亮后端（tree-sitter-highlight）就是它；运行时库纯 C11，官方明确「Dependency-free ... can be embedded in any application」，甚至支持把 `lib/src/lib.c` 单文件直接编进宿主工程。
- C API（`tree_sitter/api.h`）完备：`ts_parser_new / ts_parser_set_language / ts_parser_parse_string`、增量解析 `ts_tree_edit + ts_parser_parse(old_tree)`（编辑后不整篇重析，适合实时高亮）、查询系统 `ts_query_new / ts_query_cursor_exec`（TSQuery C API 原生可用）。
- 对 F1 的意义：语法树层面区分函数名/参数/类型/字面量（各 grammar 的 highlights.scm 用 `@function`、`@variable.parameter`、`@constant` 等 capture），是实现「变量、函数名分别不同颜色」的正确工具层级。
- 对 F2 的意义：同名符号可做成语义档（同一声明树内的 identifier 节点）或词法档（取文本再扫）。
- 成本与风险（为什么它不是主案而是组合件/进阶件）：
  - **没有控件**：tree-sitter 只产语法树，文本渲染、光标、滚动、括号配对全部自己做或配别的控件——工作量远大于 Scintilla。
  - 官方现成的 `tree-sitter-highlight` 是 **Rust crate**（crates/highlight），纯 C 工程不能直接用；C 侧要用 TSQuery 自己写「capture→颜色」映射层（参考实现可看 NppTreeSitter：tree-sitter 接入 Notepad++/Scintilla 的插件，2026-09 仍活跃）。
  - 各语言 grammar 是独立仓库（如 tree-sitter-cpp 463★ MIT），需要 vendored 一起编译（每个 grammar 就是 parser.c + parser.h，无运行时依赖，集成难度本身不高）。
- 定位建议：若 F1 的语义分层（函数名/变量名异色）是硬需求，采用 **Scintilla（控件/渲染/F3）+ tree-sitter（F1 语义、F2 精确同名）** 组合——Notepad++ 生态已经实证这条路线可行。

### 3.3 KSyntaxHighlighting（KDE 框架高亮引擎）

- Kate 同款引擎独立化，300+ 语言定义（XML 规则文件），支持**只读渲染**（Renderer 可导出 HTML）——作为「查看器」场景的引擎很对口。
- GitHub KDE/syntax-highlighting 176★（KDE 主开发在 invent.kde.org，GitHub 是镜像），2026-10-27 仍有推送；LICENSES 目录核实为多许可（MIT/BSD-2/BSD-3/LGPL/CC0 等）。
- 硬伤（相对本项目约束）：
  - C++/Qt6 API（`KSyntaxHighlighting::SyntaxHighlighter` 等），**没有 C 接口**，要做 DLL 需自己写一层 extern "C" 包装（可行但要维护）。
  - 引擎只管「F1 词法高亮」：F2/F3 不在引擎范围内（那是 KTextEditor 部件的功能），仍要自己做。
  - 语言定义依赖 XML 数据文件分发（运行期要携带 syntax 目录）。
- 适合场景：宿主本身是 Qt 程序、只要 F1、且希望语言覆盖面最大时。

### 3.4 GtkSourceView（GNOME，C 库）

- 纯 C（LGPL-2.1，GitHub 65★），功能清单明确含「Highlight the matching bracket」（F3 原生）+ 语法高亮（XML 语言规格）。
- 致命约束：深度绑定 GTK。Windows 上带 GTK 运行时不现实，排除采用；保留价值是**设计参考**（其语言规格 XML、括号配对实现思路）。

### 3.5 QCodeEditor（轻量 Qt widget，MIT）★ 自研路线的最佳参考代码

- Megaxela/QCodeEditor：465★ MIT，基于 QPlainTextEdit；自带 C++/GLSL/JSON/XML 高亮规则、QSyntaxStyle 主题、行号区、自动括号。代码量小、结构清晰，**MIT 允许整体吸收改造**。
- 括号配对高亮：主线自带 `highlightParenthesis`（ExtraSelection 实现，逻辑与 F3 需求一一对应）；同名高亮 `highlightOccurrences`（选中词→QTextDocument::find 全文 ExtraSelection）也有现成实现。
- justxi/QCodeEditor fork 已移植 Qt6 并加了 matched parentheses 高亮、Java/JavaScript/Lua/Python 规则（2★，量小但可参考 diff）。
- 风险：主线 2023-08 后未更新（约两年），需 vendored 自维护；高亮是 QRegExp 词法级，与 Scintilla 同档。
- 适配本项目：若宿主界面是 Qt 且想完全掌控控件（不做 HWND 嵌入），以 QCodeEditor 为底子改造成 CodeView.dll + extern "C" 导出，是**自研成本最低**的路线（估计人日个位数即可跑通三项功能的基本版）。

## 5. 推荐路线

### 路线 A（主推）：Scintilla + Lexilla 封装 CodeView.dll

- 结构：`CodeView.dll`（自研，extern "C" 导出）→ 内部 `Scintilla` 控件（静态链或 scintilla.dll）+ `lexilla.dll`。
- C 接口草图（与工程命名习惯对齐）：

```c
// 句柄即 Scintilla 控件的 HWND
CVHwnd   CodeView_Create(HWND a_hParent, int a_iX, int a_iY, int a_iW, int a_iH);
void     CodeView_SetText(CVHwnd h, const char* a_sUtf8);        // SCI_SETTEXT
void     CodeView_SetLanguage(CVHwnd h, const char* a_sLang);    // "cpp" → CreateLexer
void     CodeView_SetStyleColor(CVHwnd h, int a_eStyle, DWORD a_dwRgb); // SCI_STYLESETFORE
void     CodeView_EnableBraceMatch(CVHwnd h, int a_iOn);         // SCI_BRACEMATCH/HIGHLIGHT/BADLIGHT
void     CodeView_EnableOccurrenceHighlight(CVHwnd h, int a_iOn);// 取词+INDICATORFILLRANGE
```

- 交付预估：F3/F2 词法档开箱即用（各一条消息链）；F1 需做主题→样式映射表（SCE_C_* × 颜色，即 SciTE 风格 stylers 文件）；整体在现有工程上属于低风险集成。
- 参考代码：notepad4（BSD，可抄）、NotepadNext（GPL，只看思路）。

### 路线 B（F1 语义硬需求时）：A + tree-sitter 组合

- Scintilla 管渲染/交互/F3；tree-sitter（MIT，纯 C，单文件 lib.c 可编入 DLL）管 F1 分层与 F2 语义档：编辑/定位变化时增量重析（TSInputEdit），TSQuery 查 identifier 节点 → 把区间提交给 Scintilla 样式或指示器。
- 成本主要在「capture→颜色」映射层与 vendored grammar 管理；NppTreeSitter 提供了完整先例。
- 建议：先落路线 A 交付基本版，语义层作为二期增强（两者不冲突，递进式升级）。

### 路线 C（宿主界面想纯 Qt 自绘控件时）：QCodeEditor 改造

- 以 MIT 的 QCodeEditor（或 justxi 的 Qt6 fork）为底，改造为 DLL 并导出 extern "C"；F2/F3 的现成实现直接继承，F1 按 Qt 正则规则表扩展。
- 优点：不引入 Scintilla 二进制依赖、代码全可控；缺点：词法档天花板、停更需要自维护、Qt 依赖进 DLL。

### 决策树

```
F1 是否必须区分「函数名/变量名」异色？
├─ 否 → 路线 A（Scintilla+Lexilla，三项功能全部现成，纯 C 天然适配）
└─ 是 → 路线 A 先行 + 二期挂 tree-sitter（路线 B）
     └─ 若拒绝引入 Scintilla 二进制 → 路线 C（QCodeEditor 改造）+ tree-sitter
```
